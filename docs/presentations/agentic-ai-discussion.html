04 / 22Working definition

An agent is a program that takes a goal and iterates toward it — using tools, reading results, correcting itself.

The four verbs
Plan.  Act.  Observe.  Iterate.
Ignore vendor names. If a tool does these four things in a loop, it's agentic.

07 / 22The differences

What makes it different.

AI Answer · what most have used AI Agent · what we're discussing
Unit of work The next sentence or line ● A whole task, end-to-end
Input A question ● A goal — and your repo
Tools it uses None. Just text out. ● Shell · files · git · R itself
Feedback loop You read, you copy, you run ● It runs, reads output, retries
Your job Translate advice → code ● Specify · review · steer
08 / 22Time multiplier

The lift is real — if you already code.

Same task, same person. Time-on-task with answer-style help vs an agent. Anecdotal but representative — why people who already write R see the biggest jump.
Refactor 600-line script — chat help
~ 4 hrs
Refactor 600-line script — agent
~ 45 min
QAQC function for new logger — chat help
~ 2 hrs
QAQC function for new logger — agent
~ 15 min
Why? You already know what "good" looks like. You can specify, review, and push back. The agent does the typing; you do the judgment. People without that judgment don't get the same lift — and often get burned.

Refactoring a 600-line fish-survey script.

The ask
"Break analyze_fish.R into small functions with roxygen headers. Keep behavior identical. Add tests for the size-class binning logic. Don't touch anything else."
Why it matters for us
Every group has one of these scripts. The agent is happy to do tedious surgery a human keeps putting off. You read the diff and approve.
Plan, before it touches anything

3. extract to R/fish_*.R files
4. add roxygen docs to each
5. write testthat tests for bin_size_class()
6. run pipeline → compare outputs
7. leave analyze_fish.R as orchestrator

17 / 22Four patterns

Prompts that actually work.

01 · Give it context
"Use R/clean_benthic.R as the style reference. Match its function signature."
Like briefing a new hire. Don't assume it knows your repo.
02 · Constrain the output
"Only touch files under R/ and tests/. Don't change DESCRIPTION."
Limits blast radius. Makes review fast.
03 · Plan before you act
"Write a step-by-step plan first. Wait for my OK before editing anything."
Catches bad approaches cheaply.
04 · Make it show its work
"After each step, print a one-line summary and the files you touched."
You stay in the loop without watching every keystroke.
18 / 22Knowing when to stop

Knowing when to stop the agent.

It's going in circles.
Same error three tries in a row. Kill it, read the error yourself, come back with more context.
It's touching files you didn't ask for.
Scope creep. Stop, narrow the prompt, restart. Don't trust a wandering agent with commits.
Tests fail in new, creative ways.
It's patching around the problem, not solving it. Revert and describe the failure directly.
You don't understand the diff.
Hard rule. Don't merge code you can't read. Ask it to explain — or simplify — or both.
19 / 22Non-negotiable

Reproducibility and code review still win.

Same standards apply

  • Every agent change goes through git
  • Same PR review as human code
  • renv / lockfile for package versions
  • Set seeds. Document them.

What doesn't change

  • A scientist still owns every line
  • SOPs still describe what happened
  • "An agent did it" is not a citation
  • Can't reproduce it → don't ship it
20 / 22This week

Getting started — in twenty minutes.

01
Pick something small.
Not the crown-jewel pipeline. A tedious task you'd hand to a summer intern.
02
Pick one tool.
VS Code agent mode, RStudio Copilot Chat, Copilot CLI, Claude Code — any of them. Don't shop.
03
Write a real prompt.
Context, constraint, plan-first, show-your-work. The four patterns.
04
Review the diff.
Pretend it's a pull request from a stranger. Because it basically is.
05
Report back next meeting.
What worked, what didn't, what surprised you. The division learns faster than any one of us.
